How the Password Gate Works

The deployed Calorie Calculator asks for a password before serving anything — pages and the paid API route alike. This is HTTP Basic Auth enforced by a 30-line Next.js proxy. Here's the whole mechanism, end to end.

File: src/proxy.ts Mechanism: HTTP Basic Auth Config: SITE_PASSWORD env var Date: Aug 12, 2026

01The one-minute version

Everything below is detail on these four sentences.

Every request to the site passes through a small server-side function (src/proxy.ts) before it reaches any page or API route. If the environment variable SITE_PASSWORD is set and the request doesn't carry the right password, the function answers 401 Unauthorized and tells the browser "this site wants credentials." The browser shows its built-in login prompt, then automatically attaches the password to every subsequent request, so you're asked exactly once. When SITE_PASSWORD isn't set — like on your Mac during development — the gate simply doesn't exist.

02The request flow

  1. First visit: the request carries nothing. The proxy runs before every page and API route. No Authorization header → it responds 401 with the header WWW-Authenticate: Basic realm="Calorie Calculator". Nothing else is rendered — the app never even runs.
  2. The browser takes over. That WWW-Authenticate header is a standard signal browsers have understood since the 90s: they show their own username/password dialog. No login page was built — the prompt is the browser's.
  3. The retry carries the credentials. The browser re-sends the request with Authorization: Basic <base64 of "username:password">. The proxy decodes it, ignores the username (single-user site — nothing to distinguish), and compares the password to SITE_PASSWORD.
  4. Match → invisible from then on. On success the proxy calls NextResponse.next(), waving the request through to the app. The browser caches the credentials for the site and attaches them to every future request — including the fetch() calls the app makes to /api/analyze — so you log in once per browser, ever.

03The code

The entire feature is this one file. Next.js 16 runs it in front of every matched request (the convention formerly called "middleware", renamed "proxy" in v16).

// src/proxy.ts
import { NextResponse, type NextRequest } from "next/server";

export default function proxy(request: NextRequest) {
  const password = process.env.SITE_PASSWORD;
  if (!password) return NextResponse.next(); // no password configured → gate off

  const auth = request.headers.get("authorization");
  if (auth?.startsWith("Basic ")) {
    try {
      // "Basic dXNlcjpodW50ZXIy" → decode → "user:hunter2" → keep the password part.
      // slice(1).join(":") instead of [1]: passwords may themselves contain ":".
      const submitted = atob(auth.slice(6)).split(":").slice(1).join(":");
      if (submitted === password) return NextResponse.next();
    } catch {
      // malformed base64 → fall through to the 401
    }
  }

  return new NextResponse("Authentication required", {
    status: 401,
    headers: { "WWW-Authenticate": 'Basic realm="Calorie Calculator"' },
  });
}

export const config = {
  // Everything except Next's static assets and the icon
  matcher: ["/((?!_next/static|_next/image|favicon.ico|icon.svg).*)"],
};
Why the matcher excludes static assets: CSS, JS bundles, and the icon contain nothing sensitive, and gating them would just add a proxy invocation to every asset request. The pages and — critically — /api/analyze (the route that spends OpenAI credits) are all covered.

05Security properties & honest limitations

What makes this safe enough: the credentials travel inside HTTPS. Base64 is encoding, not encryption — anyone who intercepts the header can read the password — but nobody can intercept it, because Vercel serves everything over TLS. The gate's real job is modest: keep strangers and crawlers from burning OpenAI credits on /api/analyze, and it does that completely.

Known limitations, accepted deliberately for a single-user tool:

· One shared password, no accounts. There's no concept of users, roles, or sessions — everyone with the password is the same person as far as the site knows.

· No logout button. Basic Auth credentials live in the browser until it decides to forget them (usually browser restart, or clearing site data). There's no server-side session to invalidate.

· Rotation = change + redeploy. To change the password: update the env var in Vercel, redeploy, and every browser prompts again.

· The upgrade path, if this ever becomes multi-user: replace the proxy with real session auth (e.g. Auth.js) — the rest of the app wouldn't change, since the gate is entirely contained in this one file.
