02Toast foundation

Built first because three later features (delete-undo, re-log, edit confirmation) sit on top of it.

Add sonner (~3 KB, action-button support, fully styleable), mount one <Toaster /> in src/app/layout.tsx, and theme it with the app's surface/line/ink tokens so it looks native.

npm install sonner

First consumer: delete becomes undo-able. window.confirm in LogList.tsx goes away — deleting removes the row immediately and raises a toast with an Undo action. Undo re-inserts the very same row (the client still holds the full LoggedMeal, including id and thumbnail), so nothing is lost and no "are you sure?" dialog is needed.

// LogList.tsx — replaces the confirm() flow
const result = await deleteMealAction(meal.id);
if (!result.error) {
  toast("Meal deleted", {
    action: { label: "Undo", onClick: () => relogExactAction(meal) }, // re-insert same row
  });
}

03Meal log card redesign

The current card packs everything into one mono string (P 12 · C 45 · F 8) twice over — hard to scan. The redesign labels every number and aligns per-food data in real columns.

What changes: macros get real labels in a three-column strip instead of the P · C · F shorthand; per-food data becomes an aligned table with a header row and a totals row, right-aligned tabular numerals; the actions (Edit / Log again / Delete) move to a consistent footer row. The collapsed row keeps only name, time, kcal, and the macro strip — one glance, four numbers, all labeled. On narrow phones the food table drops the P/C/F columns behind a horizontal scroll rather than truncating names.

04Edit logged meals

Grams and time only — if the analysis itself was wrong, re-analyzing is the honest fix.

"Edit" in the card footer switches the food table into edit mode: each grams cell becomes a number input, and the logged time gets a <input type="time">. Changing grams rescales that food's macros linearly — the exact logic handleGramsChange already implements in AnalysisProvider, extracted into src/lib/scale.ts so both pages share it. Save calls a new server action; the totals row and day totals recompute in the same roundtrip via revalidatePath("/log").

05Quick re-log

Repeat meals without a photo, an API call, or cost.

"Log again" copies the entry's foods, thumbnail, and description into a new row stamped with the current time, then confirms with a toast ("Logged to today — Undo"). Implemented as one server action that reads the source row server-side and inserts the copy with a fresh crypto.randomUUID() — no confirmation dialog, undo covers mistakes.

06Text-only analysis

No new UI — the description field simply works on its own.

The Analyze button enables when there's a photo or non-empty description. /api/analyze makes the image field optional (rejecting only requests with neither), builds userParts without the image part, and the system prompt gains one line: when no photo is provided, estimate from the description alone and mark confidence accordingly. The thread, corrections, and logging all work unchanged; a text-only meal logs with the fallback 🍽 thumbnail.

07Daily goals & progress

The feature that turns the calculator into a tracker: a calorie target, an optional protein target, and progress everywhere you decide what to eat.

Goals live in a single-row Supabase table so both devices see the same target (localStorage would give each device its own):

create table public.settings (
  id boolean primary key default true check (id),  -- guarantees max one row
  calorie_goal integer not null,
  protein_goal integer                              -- null = no protein target
);

In the log, each day header gains the slim progress bar shown in the §03 mock (calories always; a second thinner bar for protein when a protein goal is set; past days show the bar too, as a record). Over-goal renders the fill in the accent color rather than an alarm red — this is a tracker, not a scold. On the Analyze page, a compact strip under the header shows 1 430 / 2 200 kcal · 96 / 140 g protein for today, fetched server-side.

  4. You — drop the anon policies, last Only after the secret-key deploy is live, run the four SQL statements already written in FUTURE-TASKS.md (drop the three anon policies, revoke the grants).
