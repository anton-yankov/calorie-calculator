Images: final implementation plan

Tap-to-expand images everywhere, barcode images that survive into the log, and a clear snapshot rule for product edits. Reviewed against the shared brief and the code. Ready to implement on approval.

Date: 2026-09-04 Status: awaiting approval Supersedes: image findings + the meal image behaviour brief Code changes: none yet

01Review of the shared brief

The brief and my findings agree on the diagnosis and the snapshot principle. Checking both against the code turned up eight things neither document covered.

What the brief adds, kept in this plan

  • Snapshot the image at log time. A logged meal should not point at an Open Food Facts URL or a product row that can change or disappear later. My first draft stored the external URL; the brief is right and this plan copies the image.
  • Keep the barcode as a structured field on the scanned food, not only as prose in the assumptions sentence. It costs nothing now and unlocks a future "apply this fix to past meals" tool.
  • Preview and replace stay separate on the Products tab. Tapping the picture previews it; the existing "Change image" text button still replaces it.
  • Concrete mobile requirements: whole image is the tap target, full viewport with safe-area padding, a 44px or larger close button, backdrop tap and Escape to close.

02Data model and image sizes

Three places hold images after this change. Each has a size budget chosen for where it gets loaded.

ImageLong edgeApprox. size as data URLLoaded when
Meal thumbnail160px5–8 KBLog list, every meal (unchanged)
Meal photo (new)800px80–160 KBOnly when a log thumbnail is tapped
Food image copy (new)320px15–30 KBLog list, per barcode food in the analysis JSON
Product library image640px (was 320)40–90 KBProducts tab, every product

A worst-case meal, one photo plus five barcode foods, is about 300 KB in the log action body, well under the 1 MB cap. The existing 300 KB limit on product images still holds a 640px JPEG comfortably.

Type changes

// src/lib/schema.ts
export interface FoodItem {
  // ...existing fields
  /** Barcode this food was scanned from; absent for photo or text foods */
  barcode?: string;
  /** Small JPEG data URL copied from the product at add time; absent if none */
  imageUrl?: string;
}

// src/lib/log.ts
export interface LoggedMeal {
  // ...existing fields
  /** ~800px JPEG data URL for the viewer; null if the meal has no image.
   *  Omitted from list queries and fetched on demand. */
  photo?: string | null;
}

The strict JSON schema sent to OpenAI is unchanged. The two new fields are optional client-side data that the model never sees or returns. The previous estimate that goes back with a correction is stripped of them before sending, and after a correction the images are re-attached by matching the barcode, then the food name.

Storage decision: data URL column, not Supabase Storage

Recommendation: add a photo text column on meals. It matches how every other image in the app is stored, needs no bucket, no storage policies and no signed URLs, and delete plus Undo keep working as a plain row round-trip. Supabase Storage would be the better home once photo volume matters, and the on-demand fetch action in this plan is exactly the seam where a later switch would happen: only the action's body changes, nothing on the client. At three to five meals a day this column adds roughly 150 to 250 MB a year, which the free tier database holds for a couple of years before that migration becomes worth it.

SQL to run once, before deploying:

alter table public.meals add column photo text;

No grant changes: the app uses the secret key and table-level privileges already cover new columns. The barcode_products table is untouched.

03Getting images into the meal

Two changes to the capture pipeline: barcode products keep their image through "Add to meal", and the meal cover is chosen once at log time.

  1. Catalog images arrive inline The barcode lookup route in src/app/api/products/[barcode]/route.ts requests image_front_url and, when present, fetches it server-side with a short timeout and returns it as a JPEG data URL in imageUrl. Failure means imageUrl: null, never a failed lookup. Saved products already return data URLs, so the client sees one shape for both sources.
  2. "Add to meal" copies the image onto the food barcodeProductToFood and manualProductToFood in src/lib/products.ts set barcode and imageUrl. The confirmation card shrinks the product image to 320px with makeThumbnail before adding, so the meal's JSON copy stays small while the product library keeps the 640px original.
  3. Cover chosen at log time In handleLog in src/components/AnalysisProvider.tsx: if there is a source photo, resize it if the analyse step has not already done so, then make an 800px photo and a 160px thumbnail from it. Otherwise take the first food with an image and use it for both. Otherwise both are null. This also fixes the "photo picked but never analysed" case.
  4. Corrections keep the images Before sending a correction, the previous estimate is stripped of barcode and imageUrl. When the new estimate arrives, each food is matched to the previous one by barcode first, then by normalised name, and inherits both fields. An item the model renamed without a barcode loses its picture, which is acceptable.

04One shared image viewer

A single ImageLightbox mounted once in the root layout, opened from anywhere through a small hook.

Shape

A LightboxProvider in src/app/layout.tsx owns the open state and renders one native <dialog>. Any component calls useLightbox().open({ src, alt, load? }). When load is given, the viewer opens immediately on the small image it already has and swaps to the large one when the loader resolves, so a tap never waits on the network to show something.

Why one, mounted in the layout

  • It is outside every <summary>, so taps inside the viewer cannot toggle a meal card.
  • One dialog instead of one per row, product card and food row.
  • The Analyze page's existing preview dialog in src/components/PhotoInput.tsx is replaced by a call to the same hook, so its behaviour stays identical while the code is shared.

06Server side

One new action, two adjusted ones, and validation for the new fields.

  • List query excludes the photo. listMeals in src/lib/meals.ts selects every column except photo, so the Log page payload does not change size.
  • New getMealPhotoAction(id) returns the single photo string. It is the only place that reads the column on a page load, and the only thing that would change under a future move to Supabase Storage.
  • Delete returns the row. deleteMealAction deletes with select() and returns the full meal including photo. The Log's Undo re-inserts that returned copy instead of the client's list copy.
  • Log again already reads the full row by id and copies it, so the duplicate keeps the photo with no change.
  • Validation. isValidMeal accepts photo as null or a JPEG data URL under 400 KB. Each food's optional imageUrl must be a JPEG data URL under 100 KB and barcode must match the existing barcode pattern. Anything else is rejected as invalid meal data.

07Product edits and past meals

No behaviour change. This section records the rule so it stays deliberate.

Logged meals are immutable snapshots. Editing or deleting a product on the Products tab changes only future scans. Past meals keep their name, nutrition and, after this change, their image. "Log again" duplicates the old snapshot without consulting the product. This is the correct default for a food diary.

The new barcode field on foods is what a future "apply this product fix to past meals" tool would key on. That tool is not part of this plan.

08Scope, risks and open items

Log grows without pagingPre-existing. This plan keeps the per-meal list payload almost flat (only barcode foods add 15 to 30 KB each). Paging the log is a separate piece of work worth doing before the log reaches a few hundred meals.
Older meals stay soft in the viewerThey only have the 160px thumbnail. The viewer shows it at up to twice its natural size rather than stretched to the full screen, which reads as a small preview instead of a blur.

09Implementation order

Nine steps, each leaving the app working. Run the SQL first.

  1. Run the SQL Add the photo column in the Supabase SQL editor and mirror it in supabase/schema.sql.
  2. Types and validation FoodItem gets barcode and imageUrl; LoggedMeal gets photo; isValidMeal and a new isValidFood check in src/app/actions.ts.
  3. Meals data layer and actions List without photo, getMealPhotoAction, delete returning the row, and the Log's Undo using it.
  4. Lightbox provider and viewport New src/components/ImageLightbox.tsx mounted in the layout, plus the viewport export with viewportFit: "cover". Migrate the Analyze photo preview onto it and delete the old dialog.
  5. Barcode images survive Lookup route inlines the catalog image; product-to-food helpers copy barcode and a 320px image; product library images move to 640px in ProductPhotoInput.
  6. Cover selection at log time handleLog builds photo and thumbnail from the source photo or the first food image, resizing the source itself when analyse never ran.
  7. Corrections keep images Strip the two fields before sending; re-attach on the reply by barcode, then name.
  8. Tappable surfaces Log header and food table, estimate rows, barcode confirmation, product card, product editor and manual form all open the viewer.
  9. Verify on a phone Barcode-only meal shows its image in the Log; photo-plus-barcode meal shows the photo; photo-never-analysed meal shows the photo; delete then Undo keeps the photo; viewer opens from every surface without toggling rows; close button clears the notch in the installed app. Then npm run typecheck and npm run lint.
