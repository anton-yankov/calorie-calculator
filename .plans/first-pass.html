02Architecture

Three moving parts. The API key never leaves the server — the browser only ever talks to our own API route.

No database, no storage. Photos are processed in memory and never written to disk. Everything the user sees lives in client state for the current page session.

Phone photos: resizing & quality

The problem: a phone photo is 12–48 MP (4000×3000+, 2–8 MB as HEIC/JPEG). The model doesn't need anywhere near that — vision models downscale big images internally anyway — so sending the original wastes upload time on mobile data without improving the analysis.

The approach: resize in the browser before upload. createImageBitmap(file) → draw onto a canvas at 1024 px on the long edge → canvas.toBlob("image/jpeg", 0.85). A 5 MB photo becomes a ~100–200 KB upload.

ConcernAnswer
Does quality suffer?Downscaling is a clean resample, not compression artifacts. Plates, portions, and food textures stay fully recognizable — which is all the analysis depends on. Accuracy is limited by portion-estimation ambiguity, not resolution.
What does degrade?Tiny text (e.g. nutrition labels on packaging). If we later want label reading, bump the constant to 1568–2048 px — a one-line change in lib/resize.ts.
Original photoNever modified — we only send a downscaled copy. The on-screen preview uses the full-quality local file.
Sideways photosBrowsers apply EXIF orientation during decode, so the canvas copy is always upright.
Privacy bonusRe-encoding strips EXIF metadata, including GPS location, before anything leaves the phone.
iPhone HEICSafari decodes HEIC natively; the canvas always exports JPEG, so the server and model only ever see JPEG.

03User flow

The two correction paths, precisely

PathWhat happensCost / latency
Edit grams User changes a food's grams in the table. Macros for that row scale proportionally (new = old × newGrams / oldGrams), totals recompute. Pure client-side. Free, instant
Correct & re-ask User types a correction ("that's rye bread", "there's also butter you missed"). We re-call the model with the same image, the previous JSON answer, and the correction. Model returns a full replacement result. ~$0.003, a few seconds

04API contract

One route handles both first analysis and corrections — a correction is just an analysis with extra context.

Request — POST /api/analyze (multipart form)

FieldTypeNotes
imageFile (JPEG/PNG/WebP/HEIC)Resized client-side to ≈1024 px long edge, re-encoded as JPEG
descriptionstring, optionalUser's note, e.g. "rye bread, whole milk, olive oil on the salad"
previousResultJSON string, optionalThe prior analysis — present only on correction calls
correctionstring, optionalThe user's correction text — present only on correction calls

Response — enforced by a JSON schema (structured outputs)

The confidence and assumptions fields exist so the UI can show why a number is what it is — that makes wrong guesses easy to spot and correct.

05Model call

Sketch of the server-side call. Exact SDK method names to be verified against current OpenAI docs during implementation — the shape is what matters here.

// src/app/api/analyze/route.ts
import OpenAI from "openai";

const client = new OpenAI(); // reads OPENAI_API_KEY from env
const MODEL = process.env.VISION_MODEL ?? "gpt-5.6-luna"; // swappable

const SYSTEM_PROMPT = `You are a nutrition estimation assistant.
Given one photo of food and an optional user description, identify each
distinct food item and estimate: portion weight in grams, calories, and
grams of protein, carbs, and fat.

Rules:
- Use visual cues (plate size, utensils, packaging) to judge portions.
- The user's description overrides what you infer from the image
  (e.g. if they say "whole milk", do not assume skim).
- If a correction to a previous answer is provided, produce a fully
  corrected new answer — apply the correction and keep everything
  else that was right.
- State your key assumptions per item; mark confidence low when the
  photo is ambiguous (sauces, oils, hidden ingredients).`;

export async function POST(req: Request) {
  const form = await req.formData();
  const image = form.get("image") as File;
  const b64 = Buffer.from(await image.arrayBuffer()).toString("base64");

  const userParts: object[] = [
    { type: "input_image", image_url: `data:image/jpeg;base64,${b64}` },
  ];
  const description = form.get("description");
  if (description) userParts.push({ type: "input_text",
    text: `User description: ${description}` });

  const previous = form.get("previousResult");
  const correction = form.get("correction");
  if (previous && correction) {
    userParts.push({ type: "input_text",
      text: `Previous analysis: ${previous}\nUser correction: ${correction}` });
  }

  const response = await client.responses.create({
    model: MODEL,
    input: [
      { role: "system", content: SYSTEM_PROMPT },
      { role: "user", content: userParts },
    ],
    text: { format: { type: "json_schema", name: "meal_analysis",
      schema: MEAL_ANALYSIS_SCHEMA, strict: true } },
  });

  return Response.json(JSON.parse(response.output_text));
}
Why structured outputs? Luna supports schema-enforced JSON, so the response is guaranteed parseable — no regex extraction, no retry-on-bad-JSON logic in the first pass.

08Build order

  1. Setup (~15 min) Scaffold Next.js + TypeScript with the src/ directory option (create-next-app asks), install the OpenAI SDK. Create an API key at platform.openai.com, add a few dollars of credit, put the key in .env.local.
  2. API route first Build /api/analyze and test it with curl and a few real food photos before touching UI. This is where all the risk lives — tune the prompt until the numbers look sane.
  3. Upload UI Photo picker with camera capture on mobile (<input type="file" accept="image/*" capture="environment">), client-side resize, description field, loading state.
  4. Results table Per-food rows with kcal/protein/carbs/fat, confidence badge, assumptions on tap, totals row. Editable grams with proportional recompute.
  5. Correction loop Correction text bar → re-call the route with previousResult + correction → replace the table. Done.

Realistic total: an afternoon to a day of build time; the variable is prompt tuning in step 2.

09Known limitations & open questions

Accuracy is inherently rough. Photo-based portion estimation is typically ±20–30% even for strong vision models — hidden oils, sauces, and cooking methods are invisible. The description field and correction loop are the mitigations; the assumptions field makes errors visible.

Numbers are model estimates, not database values. If first-pass quality feels off, the v2 upgrade path is: model identifies foods + grams, macros come from USDA FoodData Central per 100 g. Deliberately out of scope now.

HEIC photos from iPhone. Client-side canvas re-encoding to JPEG should handle this in Safari; needs a quick test on a real device early in step 3.

For later (explicitly deferred): meal log with daily totals, deployment for phone use anywhere, multiple photos per meal, barcode/label reading for packaged foods.
