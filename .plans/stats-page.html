Stats Page: Calories & Protein Over Time

A fourth tab that turns the meal log into trends: how many calories and how much protein you actually average, day by day and week by week, against the goals you already set on the Log page.

Route: /stats Data: existing meals + settings tables SQL: none for v1 Charts: hand-rolled SVG, no library Date: 4 Sep 2026

01The one-minute version

Everything below is detail on this paragraph.

Add a Stats tab next to Analyze, Log and Products. The page loads every meal's timestamp and totals (no thumbnails, no food lists), groups them into days in your phone's timezone exactly like the log does, and shows four stat tiles plus two charts: calories per day and protein per day, each with your goal drawn as a line and a trailing 7-day average on top. A single range control (7d · 30d · 90d · All) scopes everything. No new tables, no new API routes, no chart library: two small SVG components in the app's own palette. The rest of this document is the layout, the chart rules, the data path, the edge cases, and eleven questions where your answer changes what gets built.

A stats page hidden behind a link on the Log page would be the third option, but you asked for a page, and a tab is how this app says "page".

03What's on the page

Top to bottom: header, range control, four tiles, two identical chart cards. Nothing else in v1.

The stat tiles

TileValueCaption
Avg caloriesMean of daily calorie totals over logged days in the range, today excluded"27 logged days · goal 2,400"
Avg proteinSame, for protein grams"goal 150 g", or "no protein goal" when unset
Days at goalCount of logged days whose calories met the goal (see question 1 on what "met" means)"protein 21 of 27" as the second measure
Days loggedDays with at least one meal, out of the calendar days in the range"3 days empty"; this is the honesty tile that tells you how much the averages can be trusted

The two charts

Both are the same DailyBars component: one column per day, the goal as a labeled hairline, a trailing 7-day average as a line, hairline grid, tick labels in mono. Protein simply gets a different series, unit and goal. If no protein goal is set, the protein chart still renders, just without the goal line.

The table twin

Each chart card ends with a "Show as table" toggle, a plain <details> like the log's meal cards. It lists day, calories, protein, meals, and the delta to goal, in the same dd.mm date format the log now uses. This is what makes the page readable with a screen reader, on a printout, or when you want the exact number without hovering.

Desktop

The page keeps max-w-3xl like Log. Tiles go four across from sm. The charts stay stacked and full width, because a wider chart means more readable days, and side-by-side charts would only halve that.

04How the charts are drawn

The form and marks follow one rulebook so both charts read as one system with the rest of the app.

RuleDecision
FormColumn chart per day. The reader's job is "how did each day compare to the goal", which is magnitude against a reference, so columns plus a reference line, not a line chart. The 7-day average is the only line, and it shares the same axis and unit, so there is never a second y-axis.
ColorOne hue for the bars: the app accent #E08A5C. The goal line and the average line are ink #EDEAE0. Grid is --line. No green/red per bar: the goal line already shows over and under, and coloring bars by outcome would make every under-goal day look like a failure, which is wrong when the goal is a floor.
MarksBars capped at 24px wide with a 4px rounded top and square base; 2px surface gap between neighbors; lines 2px with round joins; end dot 8px with a 2px surface ring; grid and baseline 1px solid, never dashed.
LabelsNo number on every bar. Labeled: the goal line (at its right end), the y-axis with two or three round ticks, the first and last day on the x-axis. Everything else lives in the tooltip and the table.
LegendPresent because there are two series (daily bars, 7-day average): a small swatch and a short line key in the card header, text in muted ink.
Hover and tapThe bar's full slot (including the gap, at least 24px wide) is the hit target. Pointer over or tap shows a tooltip: date and meal count on top, then the value bold with the delta to goal, then the other measure. On touch, tap pins it and a tap elsewhere dismisses it. The hovered bar lightens slightly.
Missing daysA day with no meals is an empty slot with a tiny tick on the baseline, never a zero bar. Empty days are excluded from averages and from "days at goal".
TodayToday is drawn outlined with an 18% fill, because it is incomplete. It is excluded from the averages and the 7-day line, and labeled "today" on the axis.
Long ranges7d and 30d draw one bar per day. 90d and All switch to one bar per Monday-to-Sunday week (matching the calendar's week start), showing the weekly average per logged day, with the same goal line. The tooltip then says "Week of 25.08 · 6 logged days". Bars never get thinner than 4px.
SizingSVG rendered at the card's measured pixel width via a small ResizeObserver hook, fixed 180px plot height plus a 20px axis band, so text stays crisp at 11px and the card never gets an inner scrollbar.
MotionNone on the bars. The page uses the existing page-enter fade like every other page; refetches hold the previous render at reduced opacity rather than flashing a skeleton.
AccessibilityThe SVG carries role="img" with a one-sentence summary ("Calories per day, 6 Aug to 4 Sep, average 2,262 against a 2,400 goal"). The table twin is the keyboard and screen-reader path. Text never wears the data color.

05The data path

One light query, then everything happens on the client, for the same reason the log groups on the client: only the phone knows what day it is.

Why not aggregate in the database

Daily totals need day boundaries, and day boundaries need the viewer's timezone, which the server on Vercel doesn't have. The log already solves this by grouping with dayKey() on the client, and the Today strip solves it by having the client send ISO bounds. A SQL group by date_trunc would need the IANA zone passed in and a Postgres function to hold it, which is a real option later (sketched in §10) but not needed at this data volume.

The payload

QueryPer rowOne year at 3 meals/day
Current listMeals()~5–20 KB5–20 MB (thumbnails and food lists)
New listMealTotals()~110 bytes~120 KB

So the page fetches all totals once and the range control filters in memory. Range changes are instant and never refetch. If the table someday holds many years, the query can take a since bound for the default range and lazy-load "All", without changing anything the client does.

// src/lib/meals.ts — the only new data access
export interface MealTotalRow {
  loggedAt: string;
  totals: MealTotals;
}

export async function listMealTotals(): Promise<MealTotalRow[]> {
  await connection();
  const { data, error } = await supabase()
    .from("meals")
    .select("logged_at, totals:analysis->totals")   // PostgREST JSON path, no thumbnails
    .order("logged_at", { ascending: true });
  if (error) throw new Error(`Couldn't load stats: ${error.message}`);
  return (data as { logged_at: string; totals: MealTotals }[]).map((r) => ({
    loggedAt: r.logged_at,
    totals: r.totals,
  }));
}

// src/lib/stats.ts — pure, client-safe
export interface DayStat {
  day: string;            // YYYY-MM-DD from dayKey()
  meals: number;
  totals: MealTotals;     // sumTotals() of the day's meals
}

export function groupByDay(rows: MealTotalRow[]): Map<string, DayStat>
export function daysInRange(range: "7d" | "30d" | "90d" | "all", days: Map<string, DayStat>): DayStat[]
export function bucketByWeek(days: DayStat[]): WeekStat[]            // Monday start, per-logged-day averages
export function rollingAverage(values: (number | null)[], n = 7): (number | null)[]
What gets reused: dayKey, dayLabel and shortDate from day.ts for every date on the page; sumTotals from scale.ts for day totals; getGoals from settings.ts; the header, error card and skeleton patterns from the Log page. The week-start helper already exists in day.ts as a private function and only needs exporting.

06Rules and edge cases

Decided up front so the implementation has no judgment calls left in it.

SituationBehavior
No meals at allDashed empty state like the log's: "Nothing to chart yet. Log a few days of meals and trends appear here." Range control hidden.
Fewer days than the rangeCharts start at the first logged day, not padded with 30 empty slots. The tile caption says "12 logged days".
No goals setTiles drop the goal captions, "Days at goal" becomes "Best day" (highest calorie day), charts render without goal lines, and a one-line link to the Log page's goal editor sits under the tiles.
Calorie goal set, protein goal notProtein tile and chart render without a goal; nothing else changes.
Goal changed last weekEvery past day is compared to the current goal, because settings stores one row with no history. Accepted for v1; question 8 offers the alternative.
Backdated mealsThey land on their logged day, so the chart is always the log's truth. Editing a meal's date moves the bar on the next visit.
Timezone and DSTdayKey() uses the browser's local date, so a 23-hour or 25-hour day still counts as one day, identical to the log's grouping. Travelling across zones regroups history in the new zone, same as the log today.
Load failureThe same red error card as the log, with the message from Supabase.
Reduced motionNo chart animation exists to disable; the page-enter fade already respects the setting.
Very wide screensBars are capped at 24px and centered in their slot, so a 30-day chart on a desktop shows air between bars rather than fat blocks.

07Build order

Roughly a day of work, in an order where each step is visible on its own.

  1. Data: listMealTotals() and src/lib/stats.ts Query, grouping, week buckets, rolling average. Verify in the console against the log's day headers: the day totals must match to the calorie.
  2. Route shell: page, loading, nav tab Header, error card, skeleton, the fourth tab with the phone padding tweak. Check 375px and 360px before going on.
  3. Tiles and range control Numbers only, no charts yet. This alone is already useful and confirms the math against real data.
  4. DailyBars: bars, goal line, axes Measured-width SVG, static render. Mount it twice. Compare the calorie chart to the log by eye for a week.
  5. 7-day average, today outline, weekly buckets The second series and the two special cases. Switch ranges and make sure the goal line and axis rescale sensibly.
  6. Tooltip and table twin Pointer and touch behavior, then the details table. Run through with VoiceOver once.
  7. Revalidation and polish revalidatePath("/stats") in the actions, empty and no-goal states, README section for the new page.

None is required for v1: the page reads meals and settings through the existing service-role grants, and meals_logged_at_idx already covers the ordered scan.

Only if you answer "yes" to question 8: goal history

-- Optional. One row per goal change; the app reads the row whose
-- effective_from is the latest one at or before each day.
create table public.goal_history (
  effective_from date primary key,
  calorie_goal integer not null check (calorie_goal > 0),
  protein_goal integer check (protein_goal > 0)
);

alter table public.goal_history enable row level security;
grant select, insert, update, delete on public.goal_history to service_role;

-- Seed it from the current goals so history starts today.
insert into public.goal_history (effective_from, calorie_goal, protein_goal)
select current_date, calorie_goal, protein_goal from public.settings;

Only if the totals payload ever gets heavy: server-side days

-- Optional, later. Groups by local day for a given IANA timezone so the
-- client can request days instead of rows. Not needed at current volume.
create or replace function public.daily_totals(tz text, since timestamptz default null)
returns table (day date, meals bigint, calories double precision, protein_g double precision,
               carbs_g double precision, fat_g double precision)
language sql stable as $$
  select (logged_at at time zone tz)::date as day,
         count(*) as meals,
         sum((analysis->'totals'->>'calories')::double precision) as calories,
         sum((analysis->'totals'->>'protein_g')::double precision) as protein_g,
         sum((analysis->'totals'->>'carbs_g')::double precision) as carbs_g,
         sum((analysis->'totals'->>'fat_g')::double precision) as fat_g
  from public.meals
  where since is null or logged_at >= since
  group by 1 order by 1;
$$;
