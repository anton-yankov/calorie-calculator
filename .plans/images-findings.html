Images: lightbox, barcode photos & product edits

Three questions about how photos move through the app, answered from the code. Where something is broken, a fix is proposed. Nothing has been implemented yet.

Date: 2026-09-04 Status: findings, awaiting go-ahead Touches: Log · Analyze · Products

01Tap to expand images in the meal log

The log entry thumbnail is a 48px square inside the row's collapsible header. Making it tappable is easy; making the expanded view look good is the real work.

What is in the way

  • The stored image is tiny. On log, the meal photo is shrunk to a 160px JPEG data URL by makeThumbnail in src/lib/resize.ts, and that is the only copy saved. Blown up to a phone screen at 3x pixel density, a 160px image is a smear.
  • The image sits inside the row toggle. It lives in the <summary> of a <details> element in src/app/log/LogList.tsx. A tap on it currently opens or closes the row, so the expand control has to cancel that default.

Recommended approach

  1. Save a larger copy next to the thumbnail Add a photo column to the meals table holding an ~800px JPEG data URL. The 160px thumbnail stays for the list; the list query keeps selecting only the thumbnail so the Log page payload does not grow.
  2. Fetch the large photo on demand A small server action returns one meal's photo by id. It is called when the user taps, not on page load, so a log with hundreds of meals stays fast.
  3. One shared lightbox component Lift the native <dialog> viewer that already exists in src/components/PhotoInput.tsx into an ImageLightbox component. It already gives Escape to close, tap anywhere to close, a dimmed backdrop and a focus trap, and it works well on mobile. Reuse it for meal photos, Products tab images and the barcode confirmation card so every image in the app behaves the same way.
  4. Stop the tap from toggling the row Wrap the thumbnail in a button that prevents the default summary click, so tapping the photo only opens the viewer. The rest of the header row still expands the entry.
Existing meals: they only have the 160px thumbnail. The viewer can still open and show it, just not sharply. I lean toward showing it anyway, since a somewhat larger view is still useful, rather than hiding the control on old entries.

SQL to run in Supabase for this change:

alter table public.meals add column photo text;

02Why barcode images never reach the log

The picture is visible on the barcode confirmation card and nowhere after. It is not a display bug in the Log tab; the data simply is not there.

Where it is lost

The confirmation card in src/components/BarcodeInput.tsx renders product.imageUrl. When you tap "Add to meal", the product is converted into a food item by barcodeProductToFood in src/lib/products.ts. A food item has name, grams, calories, macros, confidence and an assumptions sentence, and no image field at all. From that point on nothing in the app knows the picture existed.

The logged meal's only image is the meal photo thumbnail, made from the camera photo in handleLog in src/components/AnalysisProvider.tsx. A barcode-only meal has no camera photo, so it gets the plate emoji placeholder.

Suggested fix

  1. Give food items an optional image Add imageUrl to the food item type in src/lib/schema.ts and set it from both barcode helpers. Saved products already store a small JPEG data URL. Open Food Facts gives an external URL, which can be stored as is.
  2. Fall back to a food image when there is no photo In the log action, when the meal has no camera photo, use the first food that carries an image as the meal thumbnail. When there is a photo, the photo wins.
  3. Show the image per row Optional but worth it: a small product image on each food row in the estimate card and in the log's food table. This also gives the lightbox from section 01 something to open per item.
One caveat: the schema sent to OpenAI is strict, so the image field stays client side only. After a text correction the model returns fresh food items, and images would be re-attached by matching food names against the previous estimate. A renamed item would lose its picture, which seems acceptable.

03Editing a product does not touch past meals

Each logged meal is a full snapshot. The Products tab edits a single lookup row, and nothing links the two.

A logged meal stores a complete copy of its foods, including name, grams, calories and macros, in the meals table's analysis JSON. Saving on the Products tab calls saveProductAction in src/app/actions.ts, which upserts one row in the barcode products table and nothing else. The only trace of the barcode inside a logged food is the free-text assumptions sentence, which is not something the code reads back.

Action on Products tabEffect on past mealsEffect on future scans
Edit name or nutritionNone. Old name, calories, macros and image stay.Next scan of that barcode uses the new values.
Change or remove imageNone.Next scan shows the new image.
Delete productNone. Meals that used it are untouched.Next scan falls back to Open Food Facts or manual entry.
"Log again" on an old mealDuplicates the old meal exactly, with the old numbers, not the product's current ones.Not involved.
This is the behaviour I'd want from a food log. A day's total should reflect what you knew when you ate. If you ever want a "fix this product and apply to the last N meals" action, it needs a barcode field on each food item first, which pairs naturally with the image field from section 02.

04Proposed next step

Sections 01 and 02 fit together as one change.

✓ imageUrl on food items ✓ photo column on meals ✓ shared ImageLightbox ✓ barcode image as fallback thumbnail ✗ propagating product edits to past meals

The food item gets an image, the meal gets a larger stored photo, and both feed the same lightbox used across the Log, Analyze and Products tabs. Product edit propagation stays out of scope unless you decide you want it.
