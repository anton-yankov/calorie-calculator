01Review of the draft

The shared plan diagnosed the three core behaviors correctly. Its lightbox direction and historical-snapshot conclusion should remain.

Draft proposalVerdictFinal-plan adjustment
Shared native-dialog lightboxKeepMake it controlled, accessible, resilient to load errors, and reusable across every visible image.
Larger meal photo loaded on demandKeepExplicitly exclude it from Log list queries and preserve it through delete/undo and “Log again.”
Add imageUrl to FoodItemChangeKeep barcode cover media in analysis-session state. Do not mix UI media into the strict OpenAI schema.
Reattach images by matching corrected food namesRemoveName matching is fragile when the model renames, reorders, splits, or combines foods.
Show images beside every food rowDeferThis was not required and would add table/layout complexity. The meal cover solves the reported Log issue.
Products edits do not rewrite historyKeepMake the same rule apply to copied cover images and re-logged meals.

Items the draft missed

  • The nutrition-label preview is another visible image and should use the same viewer.
  • listMeals() currently uses select("*"); adding a large photo without changing that query would load every full image on every Log visit.
  • Delete/undo currently restores the client’s meal object. If list results omit the large photo, undo would silently restore the meal without it unless the delete action returns the full deleted snapshot.
  • “Log again” must continue copying the original full photo as well as its nutrition snapshot.
  • The plan needs loading, failure, accessibility, safe-area, and focus-return behavior for the viewer.
  • Server Actions have a 1 MB default body limit in this installed Next.js version; generated image payloads need a deliberate size ceiling rather than an assumed resolution.
  • External Open Food Facts images can disappear or change. They can be used pragmatically, but they are not as durable as locally saved JPEG data URLs.
  • The nullable database change must be applied before code that selects the new column.

02Final product decisions

These rules remove ambiguity from implementation and QA.

Cover precedenceMeal photo → first scanned image → placeholder
Multiple barcodesFirst available product image wins
HistoryMeals remain immutable snapshots
Correction flowSession cover survives corrections
  • A fresh analysis, new photo selection, or Clear resets the barcode cover candidate. Gram edits and correction requests do not.
  • A photographed meal always uses the photographed plate as its Log cover, even when barcodes are added.
  • Existing meals remain valid. Their 160px thumbnail opens if no larger photo exists.
  • Product edits apply to future scans only. Existing meals and “Log again” retain the old nutrition and image snapshot.
  • Product-row images inside analysis and meal food tables are out of scope for this change.
Catalog-image caveat: manually saved product images are copied data URLs and therefore stable. Open Food Facts images remain external URLs in this iteration; the UI will handle failure cleanly, but long-term archival would require downloading them into owned storage.

03Image-viewer experience

One interaction pattern across Analyze, barcode entry, Products, nutrition labels, and the Log.

SurfaceTap behaviorSpecial handling
Analyze meal photoOpen immediately at best in-memory quality.Retain Change and Remove as separate controls.
Nutrition-label previewOpen the original displayable object URL.Retake remains a separate button.
Barcode confirmationOpen the catalog or saved product image.Show a neutral error if the remote image fails.
Product libraryOpen the saved product image.In edit mode, image tap previews; Change image stays explicit.
Log thumbnailOpen instantly with the thumbnail, then replace it with the large photo when loaded.Do not toggle the surrounding meal details row.
  1. Full-viewport native dialogUse 100dvh, a dark backdrop, object-contain, and safe-area padding so portrait and landscape photos remain visible on phones.
  2. Obvious, forgiving close controlsA 48px close button in the top-right safe area, backdrop tap, and Escape. Image taps themselves do not accidentally trigger unrelated actions.
  3. Accessible state managementDescriptive trigger labels, meaningful alt text, focus trap from <dialog>, cancel handling, and focus returned to the trigger after close.
  4. Progressive loadingFor Log entries, display the existing thumbnail immediately, show a subtle loading indicator, then swap in the large image. On failure, keep the thumbnail and offer Retry.

The implementation will continue using native <img> rather than next/image: these sources mix object URLs, data URLs, and externally hosted catalog URLs, and their dimensions are not known ahead of time.

04Data and persistence design

The meal stores a fast thumbnail plus an optional larger display copy. Barcode cover media stays outside the model-generated nutrition schema.

Database change

Run this SQL before deploying the application changes:

alter table public.meals add column if not exists photo text;

During implementation, update supabase/schema.sql as the canonical fresh-install schema. No migration file will be added, following the project convention.

Payload and query rules

  • Replace Log-page select("*") with explicit summary fields that exclude photo.
  • Fetch one meal’s photo by validated UUID only when its viewer opens; authenticate the action and return only the image string.
  • Generate the large meal JPEG from the already resized 1024px analysis image and enforce a conservative encoded-size cap so the entire log Server Action remains under Next.js’s 1 MB default.
  • Accept only bounded JPEG data URLs or allowlisted HTTPS Open Food Facts image URLs as persisted media.
  • Cache a fetched full image in the mounted meal row so reopening the viewer does not call the server again.

05Implementation sequence

Each phase leaves a clear verification point and avoids mixing model schema changes into UI work.

  1. Add bounded image helpers and typesExtend LoggedMeal/MealRow with nullable photo; add a reusable JPEG data-URL helper and server-side media validation. Leave FoodItem and the OpenAI schema unchanged.
  2. Persist and read full meal photos safelyCreate both image sizes at log time, add a minimal authenticated read action, and change list queries to omit the large field.
  3. Preserve lifecycle operationsEnsure update leaves media untouched, “Log again” copies it, and delete returns the complete deleted snapshot needed for Undo so the full photo is not lost.
  4. Carry the barcode cover in session statePass product.imageUrl alongside the converted food from both saved/manual and catalog paths. First non-null image wins; reset it on Clear, new photo, or a fresh replacement analysis.
  5. Extract the shared viewerMove the existing dialog behavior into a controlled ImageLightbox with focus restoration, backdrop discrimination, loading, error, and Retry states.
  6. Wire every visible image surfaceAnalyze photo, nutrition label, barcode confirmation, Product card, product editor, and Log thumbnail. Keep preview and edit/retake actions distinct.
  7. Verify and documentRun static checks/build, test the full matrix below on narrow and wide viewports, and update README behavior notes.

06Acceptance criteria

Approval of this plan means implementation will be considered complete only when every applicable check passes.

Every visible user-supplied or product image opens in the shared viewer.
The viewer works at 320px mobile width and desktop width without cropping the image.
Close button, backdrop tap, Escape, focus trap, and focus return behave correctly.
Tapping a Log thumbnail does not open or close meal details.
A photographed meal logs with a sharp large image and a fast list thumbnail.
A barcode-only meal with an image shows that image in the Log.
A barcode-only meal without an image still shows the plate placeholder.
For multiple scanned products, the first available image is the cover.
A meal photo takes precedence over all scanned product images.
Old 160px-only meals still open in the viewer without errors.
Full meal photos are absent from the initial Log-page payload.
Viewer fetch failure retains the thumbnail and exposes Retry.
Edit, delete/undo, and “Log again” preserve the full meal image.
Changing a Product leaves old meals unchanged and affects the next scan.
A broken external product image degrades to the existing placeholder.
npm run format:check, npm run lint, npm run typecheck, and npm run build pass.

Explicitly out of scope

  • Retroactively rewriting historical meals after Product edits.
  • Product images beside individual food rows.
  • Pinch-to-zoom, swipe galleries, image editing, or multi-image meal albums.
  • Downloading Open Food Facts images into owned storage; this is the logical follow-up if archival durability becomes important.
Approval gate: no application implementation begins until this plan is approved. Once approved, the work will follow the sequence and scope above, with any required Supabase SQL provided inline.

Supporting evidence

Why media stays out of FoodItem

FoodItem is the output of a strict OpenAI JSON schema. Adding client-only image data creates correction-round reconciliation work and fragile name matching. A session-level cover candidate satisfies the requested Log behavior without changing model output.

Why the large image is fetched on demand

The Log may contain hundreds of meals. Loading a roughly 1024px data URL for every row would inflate the server payload even though almost none are opened. The list needs only the 160px thumbnail.

Why Product edits remain non-retroactive

Logged meals store complete analysis snapshots and do not hold a live product relation. This protects historical totals. “Log again” intentionally copies the recorded snapshot rather than silently recalculating it.
